## 2. 一页结论

判定规则：

- **通过**：按需求实机执行，结果可重复，并且关键指标满足要求。
- **部分通过**：主要链路可用，但仍有未完成项或结果不能稳定复现。
- **不通过**：已测试，但关键指标不满足要求。
- **未测试**：缺少 MCU、PPS、功耗仪等必要条件，不能用软件模拟代替硬件验收。

| 阶段 | 需求摘要 | 本次判定 | 关键结论 |
| --- | --- | --- | --- |
| 1 | 双 IMX586 同时出图 | **通过** | 两路同时取得 4000×3000 MJPEG，各连续 100 帧，画面有效 |
| 2 | 独立 ISP Pipeline / IQ | **部分通过** | 两个独立 AIQ context 和路径有效；增益隔离通过；两份 IQ 内容完全相同，独立调参尚未完成；曝光控制曾失败一次；ISO 实际回读为 0 |
| 3 | 双路 2～4 Hz、性能与功耗 | **不通过/未完成** | 4/2 Hz 曾成功一次，但重启后不能重复，实际仍约 26/22 fps；仅完成 2 分钟压力测试；未测功耗、DDR、ISP 占用 |
| 4 | 完整驱动与 UART 控制 | **部分通过** | UART 程序、14 项协议自测和板端 115200 8N1 配置通过；无 MCU，未做真实 UART 端到端测试 |
| 5 | PPS/GPRMC/Trigger 硬件同步 | **未测试** | 10 次软件模拟触发和双帧绑定逻辑通过；无 MCU、PPS、RMC、物理 Trigger，不能证明硬件同步 |
| 6 | 曝光时间估算与照片 EXIF | **部分通过** | 两路各生成 10 张 JPEG，EXIF/CSV 写入成功；UTC 无效，曝光值为 RKAIQ 最新值而非逐帧绑定值，响应延迟未标定 |
| 7 | UVC、网口、eMMC 输出 | **部分通过** | 双 UVC + RNDIS 网络 + 双 HTTP + 双 eMMC 同时工作（HTTP 需执行 `net-start 0/1`）；USB 实际为 USB2.0 480 Mbps；满帧率保存 NV12 有队列丢帧 |

因此，不能把阶段 1～7 写成“全部验收通过”。当前可确认的是：双路图像链路已打通，控制和三个输出后端已经集成；剩余阻塞项主要是帧率硬件控制、独立 IQ 实调、真实 MCU 同步/UTC、USB3.0 协商和低帧率下的长稳态测试。

## 5. 阶段 2：左右独立 ISP Pipeline / IQ

### 5.1 独立 AIQ context 和 IQ 路径

程序启动日志显示：

```text
cid[0] ... iq:/etc/iqfiles/cam0/imx586_default_default.json
cid[1] ... iq:/etc/iqfiles/cam1/imx586_default_default.json
```

说明程序建立了两个 AIQ context，且分别从 cam0/cam1 目录加载 IQ。

但两个 JSON 的 SHA256 完全相同：

```text
d0f4a039...  /etc/iqfiles/cam0/imx586_default_default.json
d0f4a039...  /etc/iqfiles/cam1/imx586_default_default.json
```

这只能证明“路径和实例独立”，不能证明“广角和鱼眼已经做了不同 IQ 标定”。白平衡、BLC、LSC、LDC 的独立标定也未在本次测试中验收。

### 5.2 增益独立控制

测试命令：

```text
gain 0 8000
wait 2000
status all
gain 1 2000
wait 2000
status all
```

结果：

- 设置 cam0 为 `8000` 后，cam0 回读 `8000`，cam1 保持原值 `4000`。
- 再设置 cam1 为 `2000` 后，cam1 回读 `2000`，cam0 仍为 `8000`。
- 两路 `mean_luma` 分别发生变化，未发现设置一路导致另一路参数跟随变化。

增益控制隔离 **通过**。

### 5.3 曝光独立控制

测试命令：

```text
exposure 0 5000
exposure 1 20000
wait 5000
status all
```

复测成功时回读：

- cam0：`4977 us`，接近请求的 `5000 us`。
- cam1：`20072 us`，接近请求的 `20000 us`。

但第一次同类测试中，两路仍约为 `30004 us`。也就是说命令返回 `OK` 不等于传感器一定已经生效，当前结果不能稳定复现。

曝光独立控制判定为 **部分通过**，需要修复后连续重启 10 次复测。

### 5.4 ISO 与增益的区别

当前 `status` 的字段含义：

- `gain_x1000`：实际设置/回读的总增益倍率，`1000` 表示 1.0 倍，`8000` 表示 8.0 倍。
- `iso`：RKAIQ 实际 ISO 查询结果。本次一直为 `0`，因此不能称为真实 ISO。
- `estimated_iso`：程序根据增益换算给 JPEG 使用的估算值。例如 1.0 倍写为 ISO 100。

之所以必须区分，是为了避免把算法估算值伪装成传感器/AIQ 实际值。当前可以验收“增益独立设置”，不能验收“实际 ISO 独立设置和回读”。

### 5.5 判定

**部分通过。** 后续必须完成：

1. 让 cam0/cam1 使用真正不同的 IQ 内容，并分别验收 AE/AWB/BLC/LSC/LDC。
2. 修复曝光设置偶发不生效。
3. 实现实际 ISO 查询，或在协议中明确只支持 `gain_x1000`、ISO 仅估算。

## 6. 阶段 3：帧率、稳定性、性能、温度和功耗

### 6.1 4/2 Hz 功能测试

命令：

```text
fps 0 4
fps 1 2
capture-status all
wait 10000
capture-status all
```

首次测试的 10 秒计数：

- cam0：`2046 → 2086`，增加 40 帧，即 4.0 fps。
- cam1：`1970 → 1990`，增加 20 帧，即 2.0 fps。
- 该时间段两路 `sequence_drops` 没有增加。

但是程序重启后复测：

- `status` 显示目标值 `fps_x1000=4000/2000`。
- 实际 `capture-status` 约为 cam0 26 fps、cam1 22 fps。
- 10 秒帧数分别增加约 260/220，不是 40/20。
- 反向设置 2/4 fps 后也出现约 15/30 fps 的异常结果。

所以首次成功不能作为最终验收，帧率控制 **不通过**。根因应从 IMX586 VBLANK/VTS 设置、RKAIQ 帧率 API 生效顺序以及启流后重新下发时机排查。

### 6.2 2 分钟双路压力测试

该测试实际在约 26/22 fps 下运行，不是目标 4/2 fps：

| 项目 | 开始 | 120 秒后 | 增量 |
| --- | ---: | ---: | ---: |
| cam0 frames | 128 | 3254 | 3126 |
| cam0 sequence_drops | 19 | 495 | 476 |
| cam1 frames | 108 | 2757 | 2649 |
| cam1 sequence_drops | 37 | 990 | 953 |

满传感器帧率时丢帧明显，不满足稳定性要求。

### 6.3 CPU、内存与温度

- 程序初始化后的 CPU 使用率大约为一个 CPU 核的 9%～13%。
- RK3576 共 8 核，系统总 CPU 大部分时间约 98% 空闲。
- 程序常驻内存约 14.5 MB。
- 最高温度从 46.23℃ 上升到 50.846℃，约增加 4.616℃。
- 未发生 swap。

### 6.4 内核日志

观察到：

- 每次启流附近出现一次 MIPI CSI `ERR2:0xf0000`。
- 出现 `vblank need >=1000us cur696us` 告警。
- 停流时出现 ISP params stream-off event timeout。
- 未发现持续不断的 MIPI 错误风暴，但日志并不干净。

### 6.5 本阶段未完成项

- 文档要求 30～60 分钟，本次只跑了 2 分钟。
- 未分别重新测单路与双路 2/4 Hz。
- 没有功耗仪，未测待机、单路、双路功耗。
- 未采集 DDR 和 ISP 专用硬件占用计数器。

### 6.6 判定

**不通过/未完成。** 必须先修复 2/4 Hz 的可重复性，再重新做至少 30 分钟测试和功耗基线。

## 8. 阶段 5：PPS、GPRMC/NMEA、Trigger 硬件同步

### 8.1 本次只能做软件模拟

使用以下命令产生 2 Hz、共 10 次模拟触发：

```text
sync-bind-reset 0
sync-bind-log /root/camera_uart/test_20260804/stage5_bind.csv
sync-sim-start 2 10
wait 6000
sync-sim-status
sync-bind-status
sync-bind-last
time-sync-status
sync-controller-status
```

软件结果：

- 触发 10 次，`trigger_id_gaps=0`，`duplicate_triggers=0`。
- cam0 绑定 10 帧，cam1 绑定 10 帧，完整配对 10 组。
- 最后一组左右帧时间差为 314000 ns，即 0.314 ms。

### 8.2 为什么 0.314 ms 不能当作硬件同步精度

本次 `source=SIM`，相机仍是自由运行。CSV 中 `cam0_delay_ns` 和 `cam1_delay_ns` 为负数，说明程序给模拟 Trigger 匹配的是 Trigger 之前已经出现的相邻帧，而不是 Trigger 真正触发出来的帧。因此 0.314 ms 只代表两路自由运行帧恰好接近，不能代表硬件触发同步误差。

同时状态为：

```text
TIME_SYNC_STATUS state=UNLOCKED utc_valid=0 pps_events=0 rmc_events=0
XVS_CONTROLLER_STATUS configured=0 connected=0
```

### 8.3 接 MCU 后的验收条件

- 能收到连续 PPS，并且 `pps_events` 持续增加。
- 能解析 GPRMC/GNRMC，UTC 锁定后 `utc_valid=1`。
- Trigger 必须驱动两路 IMX586 的真实同步输入/同步时序。
- 每个 `trigger_id` 必须各绑定一张 cam0 和 cam1 图，不能重复、漏配。
- `trigger_to_frame_ns` 应符合传感器时序且为因果正确的正向延迟。
- 连续测试至少 1000 次，再统计左右曝光起点/中心误差的最大值、平均值和 P99。

### 8.4 判定

**软件协议和绑定结构通过，真实硬件同步未测试。**

## 10. 阶段 7：UVC、网口和 eMMC

### 10.1 双 UVC 测试

电脑同时抓取两路 30 帧，两个进程均正常退出。文件分析结果：

| 项目 | cam0 | cam1 |
| --- | --- | --- |
| 编码 | MJPEG | MJPEG |
| 分辨率 | 4000×3000 | 4000×3000 |
| 帧数 | 30 | 30 |
| SHA256 | `837491ea...dde` | `82c2cfa5...6178` |

板端 UVC 状态显示两路均已编码和发送，`encode_errors=0`。cam0 在 USB 刚枚举/刚启流时出现一次 2036 B 的 `corrupted data` 提示，随后连续帧正常；仍建议后续长测确认启动瞬间不会影响上层应用。

### 10.2 同一 Type-C 上的 USB 网络和 HTTP 图像

USB 复合设备同时提供 UVC 和 RNDIS。实测：

- 电脑到板卡 `192.168.55.1` 连续 ping 10/10 成功，丢包率 0%，平均 0.271 ms。
- HTTP cam0/cam1 均拉取到一张 4000×3000 JPEG。
- 双 UVC、双 HTTP、ping 与 eMMC 保存可在同一个 `camera_aiq_test` 进程中同时执行。

必须区分两个状态：

- `camera-uvc.service` 启动后，双 UVC 和 RNDIS 虚拟网卡会自动恢复。
- 当前服务不会自动执行 `net-start 0/1`，所以 8080 端口默认不监听。本节 HTTP 结果是在交互程序中执行 `net-start 0`、`net-start 1` 后取得的。

HTTP 启动后，电脑端直接测试，不需要 SSH 端口转发：

```bash
ping -c 10 192.168.55.1

ffmpeg -y -i http://192.168.55.1:8080/cam0 -frames:v 1 cam0_http.jpg
ffmpeg -y -i http://192.168.55.1:8080/cam1 -frames:v 1 cam1_http.jpg
```

执行 `net-start 0/1` 后，浏览器可直接打开：

```text
http://192.168.55.1:8080/cam0
http://192.168.55.1:8080/cam1
```

前提是电脑已经识别 RNDIS 网卡并获得/配置 `192.168.55.10/24`，且板端 HTTP 服务已经由 `net-start` 启动。

### 10.3 USB 实际速度

板端 UDC：

```text
udc=23000000.usb
current_speed=high-speed
maximum_speed=super-speed
state=configured
```

电脑 `lsusb -t` 也显示 UVC 和 RNDIS 均位于 `480M` 链路。因此：

- 控制器最大能力是 SuperSpeed。
- 本次实际协商仅为 High-Speed，即 USB2.0 480 Mbps。
- 不能写成“USB3.0 测试通过”。

当前设备经过电脑 USB2 hub 分支枚举。要验证 USB3.0，应使用确认支持 SuperSpeed 的 Type-C 数据线，尽量不经过 USB2 hub，接电脑 USB3.x 端口，再确认设备出现在 `5000M` 或更高速率分支。

### 10.4 eMMC 保存

短时间双路保存：

- cam0 保存 13 帧，共 234 MB。
- cam1 保存 15 帧，共 270 MB。
- `save_failures=0`。

全负载测试目录：

- cam0：95 个 NV12，约 1.6 GB。
- cam1：107 个 NV12，约 1.8 GB。
- 写文件失败为 0，但保存队列出现丢帧。

一帧 4000×3000 NV12 为 18,000,000 B：

- 双路 30 fps 理论原始数据量约 1080 MB/s，普通 eMMC 不可能逐帧无损写入。
- 目标 cam0 4 fps + cam1 2 fps 时也约 108 MB/s，仍需实测 eMMC 持续写速度。
- 若要求长时间不丢帧，应先稳定 2～4 Hz，或改存 JPEG/H.264/H.265，而不是满帧率保存原始 NV12。

测试后板卡根分区为：

```text
/dev/root  28G  used 22G  available 4.4G  use 84%
```

本次未删除原始测试文件。继续测试前应先由负责人确认哪些文件可以清理，不能直接删除。

### 10.5 停机清理告警

退出程序时出现 RKAIQ pool item still in use 和 params stream-off timeout 告警。重新启动服务后双路恢复正常，但发布前仍应检查各输出线程退出、队列清空和 AIQ deinit 顺序。

### 10.6 判定

**三个输出后端的功能及同时运行通过；HTTP 当前需要命令启动，尚未配置为随服务自动启动；USB3.0、满负载无丢帧和长时间稳定性未通过。**

## 11. 小白可照做的完整复测流程

### 11.1 测试前准备

1. RK3576 使用独立电源供电。
2. 用支持数据传输的 Type-C 线连接板卡 OTG/Device 口和电脑。
3. 调试串口连接电脑，避免停止 USB 服务后无法再登录板卡。
4. 两个 IMX586 均已接好，测试期间不要带电插拔 MIPI 排线。
5. 电脑安装 `v4l2-ctl`、`ffmpeg`、`ffprobe`、`lsusb`。
6. 当前未接 MCU，所以阶段 4 的真实串口和阶段 5 的硬件同步应标记“未测试”。

### 11.2 先检查板卡最终服务

板卡端执行：

```bash
systemctl is-enabled camera-uvc.service
systemctl restart camera-uvc.service
systemctl status camera-uvc.service --no-pager
```

应看到 `enabled` 和 `active (running)`。

电脑端执行：

```bash
lsusb | grep 2207:0017
lsusb -t
v4l2-ctl --list-devices
ping -c 10 192.168.55.1
```

应看到两组 UVC 接口、一个 RNDIS 接口和 0% ping 丢包。`lsusb -t` 若为 `480M`，只能记为 USB2.0。

### 11.3 测试双 UVC

电脑端两个终端同时执行，或用后台方式：

```bash
ffmpeg -y -f v4l2 -input_format mjpeg -video_size 4000x3000 \
  -framerate 10 -i /dev/video0 -frames:v 100 cam0_100f.mjpg &
PID0=$!

ffmpeg -y -f v4l2 -input_format mjpeg -video_size 4000x3000 \
  -framerate 10 -i /dev/video2 -frames:v 100 cam1_100f.mjpg &
PID1=$!

wait "$PID0"
wait "$PID1"
```

检查：

```bash
ffprobe -v error -count_frames -show_entries stream=codec_name,width,height,nb_read_frames cam0_100f.mjpg
ffprobe -v error -count_frames -show_entries stream=codec_name,width,height,nb_read_frames cam1_100f.mjpg
```

两路都应为 MJPEG、4000×3000、100 帧。

### 11.4 测试 HTTP 网口输出

当前 `camera-uvc.service` 只自动恢复 UVC 和 RNDIS，不会自动监听 8080。无 MCU 时必须通过调试串口操作，因为停止服务后 USB 虚拟网卡可能暂时消失，不能依赖 USB SSH 会话继续操作。

板卡调试串口中执行：

```bash
systemctl stop camera-uvc.service
cd /root/camera_uart
./camera_aiq_test
```

在 `camera-aiq>` 提示符下输入：

```text
stream-start all
uvc-start all
net-start 0
net-start 1
wait 3000
net-status all
```

看到两路 `running=1` 后，电脑端执行：

```bash
ffmpeg -y -i http://192.168.55.1:8080/cam0 -frames:v 1 cam0_http.jpg
ffmpeg -y -i http://192.168.55.1:8080/cam1 -frames:v 1 cam1_http.jpg
file cam0_http.jpg cam1_http.jpg
```

两张图都应为 4000×3000 JPEG。这里走同一根 USB 线上的 RNDIS，不需要执行 SSH 隧道命令。若提示 `Connection refused`，先检查板端是否已经执行 `net-start 0/1`，不能只检查虚拟网卡能否 ping 通。

### 11.5 进入交互程序测试控制命令

保持 11.4 的交互程序运行，在 `camera-aiq>` 提示符下继续按顺序输入：

```text
status all
capture-status all
uvc-status all
net-status all

gain 0 8000
wait 3000
status all

gain 1 2000
wait 3000
status all

exposure 0 5000
exposure 1 20000
wait 3000
status all

fps 0 4
fps 1 2
capture-status all
wait 10000
capture-status all
```

判定方法：

- cam0 改增益后，cam1 增益不应改变；反之相同。
- 曝光回读应接近 5000/20000 us，而不是都停在 30004 us。
- 10 秒内 cam0 帧数应增加约 40，cam1 应增加约 20。
- 不能只看 `OK command=fps` 或 `status` 的目标值，必须比较两次 `capture-status` 的实际帧计数。

### 11.6 测试模拟同步和 EXIF（无 MCU 时仅验证软件）

在同一个 `camera-aiq>` 中输入：

```text
sync-bind-reset 0
sync-bind-log /root/camera_uart/retest_stage5_bind.csv
photo-start 0 /root/camera_uart/retest_stage6_cam0
photo-start 1 /root/camera_uart/retest_stage6_cam1
sync-sim-start 2 10
wait 6000
photo-stop 0
photo-stop 1
sync-sim-status
sync-bind-status
sync-bind-last
photo-status all
time-sync-status
sync-controller-status
```

只可以检查：10 个 trigger_id 是否连续、每路是否保存 10 张、EXIF 是否可解析。因为无 MCU，`utc_valid=0`、`configured=0` 是预期结果，这一步不能写成硬件同步通过。

### 11.7 测试 eMMC 保存

先检查剩余空间：

```bash
df -h /
```

空间足够时，在 `camera-aiq>` 输入：

```text
save-start 0 /root/camera_uart/retest_emmc_cam0
save-start 1 /root/camera_uart/retest_emmc_cam1
wait 1000
save-stop 0
save-stop 1
capture-status all
```

本机目前仅剩约 4.4 GB，不要长时间保存。检查 `save_failures=0`，并同时观察 `save_queue_drops` 是否增加。

### 11.8 测试完成后恢复客户运行状态

交互程序中输入：

```text
stream-stop all
quit
```

板卡 shell 执行：

```bash
systemctl restart camera-uvc.service
systemctl is-active camera-uvc.service
```

电脑再次执行：

```bash
lsusb | grep 2207:0017
v4l2-ctl --list-devices
ping -c 3 192.168.55.1
```

确认服务、双 UVC 和 USB 网络均恢复。

这里不检查 HTTP，因为当前服务重启后不会自动执行 `net-start`。若客户要求上电后无需 UART 命令即可浏览 HTTP 图像，需要另行修改服务启动策略；若需求是由 MCU/UART 控制输出，则应由 MCU 发送 `net-start`。

## 12. 下一轮必须优先解决的问题

1. 修复 FPS 生效顺序和 VTS/VBLANK 控制，使 4/2 Hz 在冷启动、热重启和服务重启后都可重复。
2. 连续重启 10 次验证两路曝光 5000/20000 us，定位第一次仍为 30004 us 的原因。
3. 明确协议到底要求“增益”还是“实际 ISO”；若要求 ISO，需要完善 AIQ 实际 ISO 查询和换算依据。
4. 生成真正不同的 cam0/cam1 IQ，完成广角/鱼眼 AE、AWB、BLC、LSC、LDC 验收。
5. MCU 接入后做真实 115200 8N1、PPS、GPRMC/NMEA、Trigger 和 XVS 全链路测试。
6. 将曝光信息绑定到准确的 frame_id，并标定 IMX586 Trigger 到曝光起点/中心的响应偏移。
7. 使用 USB3 数据线和直连 USB3 端口，把 `current_speed` 和 `lsusb -t` 验证到 5000M 以上。
8. 在稳定 2/4 Hz 下进行 30～60 分钟双路 + UVC + HTTP + eMMC 长测，再测待机/单路/双路功耗。
9. 修复退出时 RKAIQ pool/params timeout 清理告警。
10. 明确 HTTP 启动策略：由 MCU/UART 发送 `net-start`，或改为服务上电自动启动，并为两种策略补充验收测试。
